## 4. 多視窗去重與遞迴的影響

**去重位置**：`AppDelegate.application(_:open:)` `AppDelegate.swift:26-31`
- 去重鍵是 `url.deletingLastPathComponent().path`，也就是**父資料夾路徑**，並保留每個父資料夾的第一個 URL。
- 這個去重只發生在一次 open 事件的 URL 陣列內，不會查詢既有視窗。
- 去重後逐個呼叫 `ImageWindowController.open(with:)`。在復用模式下，每次呼叫都會 `loadFolder` 覆寫同一個視窗，所以最終顯示的是最後一個 folder。
- `ImageWindowController` 本身沒有「依 folder path 找既有視窗」的邏輯。`current` 只取 key/main/最後一個視窗（`ImageWindowController.swift:14-17`）。

**對遞迴的影響（推論，需驗證）**
- 去重鍵是父路徑，與子資料夾深度無關。若使用者一次開 `/a/b/` 與 `/a/c/` 兩個資料夾，兩者父路徑皆為 `/a`，第二個會被丟掉。這是既有的 bug 疑慮：`deletingLastPathComponent` 對資料夾 URL 語意錯誤。目前 Info.plist 未宣告資料夾型別，所以觸發條件較窄。
- 若新功能讓同一棵樹底下的多個檔案被展開，各檔的父路徑不同（`/root/x/a.jpg`、`/root/y/b.jpg`），去重不會合併它們，會連續呼叫 `open(with:)`。在復用模式下最後一次會覆寫前面的結果。
- `ImageFolder.init(containing:)` 沒有遞迴，`init(folderURL:)` 只有頂層掃描加 BFS 找第一個子資料夾，因此目前沒有「收集全部巢狀圖片」的路徑。

## 5. createWindow 的預先尺寸流程是否依賴 folder 內容

`ImageWindowController.createWindow` `:53-129`，有三段尺寸邏輯：
1. **連續捲動模式** `:56-60`：固定寬度 `Constants.continuousScrollNewWindowContentWidth`，高度為 `minWindowContentHeight`，**不依賴 folder**。之後 `:81-96` 用螢幕 `visibleFrame` 展開高度，也不依賴 folder。
2. **一般模式** `:62`：`savedOrDefaultWindowSize()`（`:132-141`，取 `lastWindowWidth/Height` 或螢幕 80%），不依賴 folder。
3. **預先依圖片縮放** `:97-121`：條件為 `!settings.dualPageEnabled`、`(alwaysFitOnOpen || resizeWindowAutomatically)`，且 `folder?.currentImage?.url` 存在，並能讀到 `ImageLoader.imageHeaderSize(at:)`（`ImageLoader.swift:228`）。

   - 計算由 `presizedContentSize`（`:165-178`）完成，依 `FittingCalculator` 與狀態列高度換算。
   - 讀的是 `ViewerSettings.load()` 的**全域** `dualPageEnabled`，而非 per-folder 覆寫。原因是 per-folder 覆寫要到 `viewDidAppear`（`ImageViewController.swift:136`）才套用，晚於 `createWindow`。推論：若某資料夾 per-folder 設為雙頁，而全域為單頁，預先尺寸仍會依單頁計算。
4. **之後的修正**：`ensureUsableWindowSize` `:259-270` 只在 `async` 中檢查視窗是否小於最小尺寸，不讀 folder。

`ImageViewController.openFitViewport` `ImageViewController.swift:657-666` 也會在載入時用螢幕尺寸重算 fit，與上述預先尺寸是獨立的第二條路徑。
